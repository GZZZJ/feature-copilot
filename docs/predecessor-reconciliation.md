## 为什么出现三套数字

|口径|宽表|特征|来源与含义|
|---|---:|---:|---|
|头部宣传口径|127|约 48,000+|README、SKILL、index 的概述，README 明确说特征数为约数且会随迭代变化|
|18 类分类汇总|127|51,092|README 与 `references/index.md` 的逐类数字加总|
|逐表标题相加|127 个逻辑标题 / 128 条候选表记录 / 127 个去重表名|54,170|8 份分类文档的 `### 表名 | N特征` 标题；一个合并标题内有两个物理名，其中一个也在独立标题出现，因此候选行不能直接汇总|

`126` 是旧的简化正则只识别单表标题时得到的数量，不是文档真实的逻辑表目录数；解析合并标题后为 127。

## 结论

- **表数量**：可暂以“127 个文档逻辑表单元 / 127 个去重表名”作为候选目录口径；AppList 合并条目保留为多来源候选，不能按 128 条导入行汇总。
- **特征数量**：不能选定其中任何一项作为正式事实。`48,000+` 是过时/近似宣传口径；51,092 与 54,170 分别来自类别摘要和逐表声明，存在 3,078 条差异。合并标题中的 783 条特征没有按两个物理表拆分，不能据此再推导单表准确数。
- **原因未验证**：可能是文档迭代未同步、合并/拆分表计数规则不同、字段增删后未回填，或各分类统计范围不一致。没有字段字典或数据平台实证，不能进一步归因。

## 迁移策略

1. 使用 `scripts/import_dz_legacy.py` 生成只读、可追溯的 staging 候选。
2. `dz_feature_candidates.csv` 中的显式字典映射保留文件行号与 hash，但保持 `pending_review`，不写入正式 `knowledge/features.csv`。
3. 宽表、上游和命名规则同样作为候选；上游类型统一标为 `unclassified_upstream`，不假定其为可信基础表。合并标题中引用自身成员的“上游表”不导出血缘边。
4. 以 DP 表字典、SQL/Python 逻辑、负责人确认作为提升到正式知识的唯一依据。
