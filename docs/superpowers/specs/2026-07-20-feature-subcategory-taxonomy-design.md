# 特征小类业务语义化设计

## 1. 背景

当前 Web 将维护包的 `feature_category` 展示为“特征大类”，将底层
`group_code/group_name` 直接展示为“特征小类”。这使业务导航与加工血缘耦合：

- 当前四个维护包包含 88 个物理特征组；小类名称中混入表名、版本、人群、窗口和加工批次。
- 同一业务主题被拆成多个小类，例如还款能力 V1/V2/衍生、DCP 交易表 1～7。
- 一个物理宽表也可能包含多个业务主题，不能始终按组名准确表达特征含义。
- 模型同学寻找特征时首先关注风险信号的业务含义，而不是 SQL 加工归属。

因此需要将“业务小类”和“加工特征组”拆成两个独立字段，并保留两者之间的可追溯关系。

## 2. 目标

1. 将“特征小类”调整为稳定、可理解的业务语义分类。
2. 保留 `group_code/group_name` 作为“加工特征组”，继续支持逻辑和血缘查询。
3. 默认按特征组批量分类，允许跨语义宽表按具体特征覆盖。
4. 保证全部受控特征都有且只有一个主业务小类。
5. 不破坏现有特征 Key、加工逻辑、血缘和分页稳定性。

## 3. 非目标

- 本次不建设自动语义分类模型。
- 本次不改变四个维护包的范围，也不重新定义特征大类。
- 本次不修改特征加工 SQL、DP 任务或生产表。
- 本次不一次性建设完整标签平台；仅预留来源、时间窗口、计算形态、客群和资产范围标签。
- 本次不将历史 `classifyTreeNodeList` 直接作为正式分类事实源。

## 4. 推荐信息架构

```text
特征大类（来源包）
  └─ 特征小类（业务语义）
       └─ 加工特征组（group_code/group_name，可选下钻）
            └─ 具体特征
```

三个层级职责如下：

| 层级 | 回答的问题 | 稳定性要求 |
|---|---|---|
| 特征大类 | 特征来自哪个受控资产包 | 随维护范围变化 |
| 特征小类 | 特征描述什么业务对象或风险信号 | 稳定，不随表版本变化 |
| 加工特征组 | 特征由哪组逻辑加工、如何追溯 | 可随工程演进变化 |

## 5. 第一版业务小类

| 编码 | 名称 | 纳入范围 | 排除范围 |
|---|---|---|---|
| `external_credit_risk` | 外部多头与征信风险 | 外部查询、多头申请、机构分布、报文变化和外部风险信号 | 内部订单和内部交易 |
| `account_credit_limit` | 账户与授信额度 | 账户状态、授信、可用额度、额度使用率和调额 | 支付交易、还款表现 |
| `loan_application_order` | 借款申请与订单 | 申请、授信流程、支用、订单阶段和借款历史 | 支付渠道类交易 |
| `transaction_payment` | 交易与支付行为 | 交易金额、渠道、时段、频次、成功失败 | 信贷订单生命周期 |
| `repayment_behavior` | 还款行为与还款能力 | 实还金额、方式、时间、应还/实还表现和能力指标 | 未来压力和逾期负担 |
| `delinquency_pressure` | 逾期与偿债压力 | 逾期、扣款失败、还款意愿、未来负担和压力趋势 | 普通按时还款行为 |
| `debt_refinancing_cost` | 负债、费用与借新还旧 | 负债结构、借新还旧、资金交叉和信贷费用 | 单一还款动作 |
| `app_device_location` | App、设备与位置行为 | App 安装、设备、页面行为、埋点、LBS 和 GPS | 电话触达和催收 |
| `contact_collection_marketing` | 联系、催收与营销响应 | 呼叫、联系结果、催收备注、营销触达和响应 | App 页面点击 |
| `customer_profile_qualification` | 用户基础与资质信息 | 身份、职业、收入等静态属性 | 借贷行为和交易行为 |

编码一经发布不得因展示文案调整而变化。新增小类必须说明与现有分类的边界，并通过配置版本升级进入。

## 6. 分类规则

### 6.1 主分类规则

- 每个特征必须有且只有一个主业务小类。
- 分类依据是特征最终表达的业务信号，不是来源、表名或计算方式。
- 百融、同盾、掘金、内部属于来源维度，不写入小类名称。
- 趋势、衍生、占比、V1/V2、`new`、`jqh`、时间窗口属于辅助属性，不作为业务小类。

### 6.2 继承与覆盖

采用“组级默认、特征级覆盖”的确定性规则：

1. 先读取具体 `feature_code` 的覆盖配置。
2. 无覆盖配置时，继承所属 `group_code` 的默认业务小类。
3. 两级都未命中时，索引构建失败，不静默归入“其他”。

必须进行特征级复核的典型物理组包括：

- 还款授信表 3/4；
- 借还额度负债交叉宽表；
- 轻资产授信及交易特征；
- 轻重资产 CROSS 特征；
- 同时包含还款响应与基础属性的催收备注组。

### 6.3 边界判断

- 借款申请与订单 vs 交易与支付：前者关注信贷生命周期，后者关注支付渠道、金额、时段和频次。
- 还款行为与能力 vs 逾期与偿债压力：前者关注已发生的还款动作，后者关注失败、逾期和未来负担。
- 负债与借新还旧：仅收跨账户、跨资产或借款—还款关系信号，普通还款不进入该类。
- 跨类比值或交叉特征：按输出指标主要解释的风险含义分类，不单设“交叉衍生”业务小类。

## 7. 配置与数据模型

新增受控配置 `knowledge/config/managed_feature_taxonomy.json`，建议结构：

```json
{
  "schema_version": 1,
  "subcategories": [
    {
      "code": "transaction_payment",
      "name": "交易与支付行为",
      "description": "交易金额、渠道、时段、频次和成功失败行为",
      "sort_order": 40
    }
  ],
  "group_defaults": [
    {
      "group_code": "fg.off.usr.pdm_risk_dz_model_daily_dcp_trade_feature_info1_df",
      "subcategory_code": "transaction_payment"
    }
  ],
  "feature_overrides": [
    {
      "feature_code": "ftr.off.usr.example_table.example_feature",
      "subcategory_code": "account_credit_limit",
      "reason": "该宽表跨业务主题，当前指标表达额度使用"
    }
  ]
}
```

`managed_features` 增加：

- `business_subcategory_code`：稳定查询值；
- `business_subcategory_name`：索引构建时固化的展示快照。

现有 `group_code/group_name` 不改名、不删除。

`feature_code` 继续沿用当前 `managed_features` 主键和跨维护包去重规则，必须全局唯一。若同一
`feature_code` 在多个包中出现，其业务分类仍只有一份；加载阶段发现同 Key 的分类事实冲突时构建失败，
不引入包名或组名复合主键。

## 8. 查询与界面设计

### 8.1 筛选项

列表页调整为：

1. 特征大类：维护包，单选；
2. 特征小类：业务语义，选择大类后展示该大类实际拥有的小类；
3. 加工特征组：可选，选择大类或小类后展示可用组；
4. 特征 Key、特征名：保持现有包含匹配；
5. 所有已填写条件继续按 AND 组合。

列表增加“特征小类”列，现有“特征组”列继续展示 `group_name`。详情页同时展示业务小类和加工特征组。

### 8.2 API 兼容

- `GET /api/v1/features` 新增 `business_subcategory`，值为业务小类编码；新增 `feature_group`，值为 `group_code`。
- 旧 `feature_subcategory` 当前按 `group_code` 精确过滤；兼容期内保持该语义，并作为 `feature_group` 别名。新 Web 不再生成旧参数。
- `feature_group` 与旧参数同时提交：去除首尾空白后相同则接受，不同则返回 HTTP 400；空字符串按未提交处理。
- 同一参数重复、业务小类编码不存在、加工组不存在或加工组不属于已选大类时返回 HTTP 400。
- `business_subcategory` 与 `feature_group` 可同时提交并按 AND 过滤；二者归属冲突时返回空列表。
- `GET /api/v1/feature-taxonomy` 返回“大类 → 业务小类 → 加工特征组”，每级包含稳定 `value`、展示 `label` 和去重特征数 `count`。
- `GET /api/v1/features/<feature_key>` 增加业务小类编码和名称，保留原加工组字段。

## 9. 校验与失败处理

索引构建前必须校验：

- 小类编码唯一、名称非空、排序值稳定；
- `group_defaults` 中的组存在于当前维护范围；
- `feature_overrides` 中的特征存在且所属组存在；
- 不允许同一组或特征出现冲突映射；
- 最终分类覆盖率必须为 100%；
- 小类引用必须指向已声明编码。

覆盖率分母是 `load_managed_catalog` 按当前 `maintenance_scope.json` 加载受控 package、并按全局唯一
`feature_code` 去重后的 `managed_features` 集合。组分母是该集合实际出现的唯一 `group_code`，不是历史
元数据快照中的全部组。审计报告同时输出源记录数、唯一特征数、唯一组数、组级默认命中数、特征级覆盖数和未分类数。

新配置校验失败时，不替换已有可读索引；Web 延续现有降级机制并报告构建错误。

## 10. 迁移步骤

1. 建立 10 个小类的受控字典。
2. 对 88 个物理特征组建立默认映射。
3. 对跨语义组抽样并建立特征级覆盖。
4. 生成迁移审计报告：各大类/小类/特征组数量、未分类数、覆盖数和覆盖原因。
5. 扩展索引、服务和 API，保留旧参数兼容。
6. 调整 Web 筛选和展示。
7. 运行全量校验、API 测试、Web 测试和回归测试。

迁移不修改事实源 JSON；分类配置是独立、可审计的产品治理层。

## 11. 验收标准

- 受控特征业务小类覆盖率为 100%，且每个特征只有一个主小类。
- 88 个现有加工组全部保留并可筛选、可追溯。
- 选择大类后，小类列表不再直接展示表名、版本或加工批次。
- 大类、小类、加工组和关键词组合查询均按 AND 返回正确结果。
- 旧 `feature_subcategory=<group_code>` 查询在兼容期内行为不变。
- 分类字典计数与列表查询计数一致。
- 业务小类名称调整不改变稳定编码和既有查询。
- 构建失败不会覆盖上一个可用索引。

计数和自动化验收口径：

- 所有 `count` 均按全局唯一 `feature_code` 计数，并在分页前计算；
- 大类计数在大类范围内去重，小类和加工组计数在父级范围内继续过滤后去重；
- 列表 `total` 是应用全部筛选条件后的分页前总数；
- fixture 至少覆盖：两个大类共享同一业务小类、组级默认、特征级覆盖、跨包重复 Key、兼容参数同值/冲突、非法编码、归属冲突空列表，以及 taxonomy 计数与列表 `total` 的对应关系。

## 12. 风险与取舍

| 风险 | 判断 | 控制方式 |
|---|---|---|
| 组级映射误伤跨语义宽表 | 高 | 特征级覆盖、抽样审计、强制覆盖率校验 |
| 小类边界随业务理解变化 | 中 | 稳定编码、边界说明、配置版本化 |
| API 参数语义变化破坏旧链接 | 高 | 新参数承载新语义，旧参数保留组查询兼容 |
| 一次性人工逐特征分类成本过高 | 高 | 组级默认覆盖主体，仅复核高风险组 |
| “外部多头与征信风险”仍较宽 | 中 | 保留加工组下钻，后续以机构维度、报文范围和计算形态标签细化 |

## 13. 后续演进

第一版稳定后，可增加独立标签维度：

- 时间窗口；
- 统计方式；
- 计算形态；
- 资产范围；
- 客群；
- 来源机构。

这些标签用于组合筛选，不改变业务小类主分类，也不重新耦合加工特征组。
